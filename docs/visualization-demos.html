1. Dominator Sunburst

Shows the shape of dominator ownership. Uses d3-hierarchy partition() + manual SVG arc paths. Zero new packages — d3-hierarchy is already installed.

Click any arc to drill in. Click center circle to zoom out.

What to look for: Wide arcs at any depth mean one child dominates its parent's retained heap. A single arc spanning >80% of a ring means nearly all of that owner's retained memory sits under one child — inspect that child first. (Ownership chain, not necessarily a direct field reference.)
In the report, this is a drill-in view from a selected dominator row — not a top-level section.

2. Retention Flow Sankey

Concept only, not a current report field. Synthetic, conserved shallow-byte path budget through a selected dominator subtree; self/unshown remainder is not drawn. The existing capped type_ref_graph.retained_weight is non-conservative and must not drive this chart. Uses installed d3-sankey; prefer the A2 pair table until a bounded additive producer exists.

What to look for: Link widths illustrate one possible exclusive partition of the sample's shallow bytes, not measured reference traffic or exact bytes freed by cutting an edge. Show self/unshown remainder and scope before shipping. The default UI should instead use A2's sortable pair table.

3. Who-Holds-Whom Heatmap

Matrix of dominator→dominated class pairs, colored by retained bytes. Pure CSS — no library needed.

What to look for: Dark blue cells indicate high-retention dominator→dominated relationships. A single dark row means one class dominates many others. A single dark column means many classes retain the same type (often byte[] or String).

4. Biggest Retention Drops

Stacked bars showing how much each dominator absorbs vs passes to its largest child. Sorted by drop size. Pure SVG.

What to look for: Large red segments mean significant retained heap is spread across siblings and own shallow bytes rather than flowing to one dominant child. This often means many small children or significant own fields — drill into those objects to understand the split.

5. Blame Propagation Bars

Each node in the retention chain shows what fraction of the parent's retained heap flows through it. Pure CSS.

What to look for: Red bars (>70%) mean nearly all of the parent's retained heap flows through that single field. Follow the chain of red bars from GC root to leaf to find the critical retention path. Caveat: this shows one dominator chain — alternative reference paths to the same object may exist but are not shown here.

6. Growth Sparklines

Inline SVG sparklines showing retained-heap trend across N snapshots. 10 lines of SVG, zero dependencies.

ClassRetained (latest)DeltaTrend

What to look for: Upward-trending sparklines show classes growing across snapshots — investigate them first, but compare captures from the same workload phase. Two snapshots show a delta, not a trend. Each sparkline uses its own min–max scale; compare shapes (trends) rather than heights across rows.

7. Category Budget Breakdown

App vs Framework vs JDK heap ownership as a proportional bar. Uses the category_rollup data that is already emitted but never rendered. ~15 LOC.

What to look for: If "Application" dominates, your own code is the primary consumer — review your data structures. If "Framework" or "JDK" dominate, look for framework-level caching or JDK internal overhead (classloaders, compiled code caches).

8. Thread State Breakdown

Threads grouped by JVMTI state, sized by retained heap. Proportional bar. Pure CSS.

What to look for: Thread state is context, not a verdict: WAITING is normal for pool workers. What matters is which individual threads retain a lot — see the per-thread view (E3) and stale ThreadLocals (E2).

9. Framework Footprint

Per-framework retained bytes. framework_analysis is always-on but never rendered.

What to look for: Frameworks with high retained bytes but few instances are holding large internal structures (caches, metadata registries). Check if framework caches can be bounded or if unused framework features can be disabled.

10. Waste Breakdown

Reclaimable memory by source. waste_summary data rendered as a proportional bar.

What to look for: The largest segment is your highest-ROI fix. Duplicate strings and empty collections are usually the top two — both fixable with zero functional changes (string deduplication, lazy-init collections).

Research-Driven Demos (J–N)

Additional visualizations from the ideas catalog. Category IDs (J1, K3, etc.) reference VISUALIZATION_IDEAS.md.

11. Boxed Number Waste (J1)

Shows memory wasted on boxed primitives (Integer, Long, Double, etc.) that could use primitive fields instead. Data: BoxedNumberRow[] — always-on, shown today only as a table.

12. Memory Waste Category Dashboard (J5)

HeapHero-inspired composite view: estimated optimization opportunity across 8 waste categories. Each bar links to the relevant report section. Data: derived from WasteSummary, DupStrings, BoxedNumberRow[], HeaderOverheadRow[], etc.

13. Retention Multiplier Scatter (K3)

Scatter plot of shallow size (x) vs retained size (y) per class. Points far above the diagonal are "leverage points" — fixing them frees disproportionate memory. Data: HistRow[] (always-on).

14. Per-Thread Memory Budget (E3)

Horizontal bar chart of threads sorted by retained heap. Immediately surfaces "one thread retains 80% of heap" patterns. Data: ThreadInfo.retained (always-on). Inspired by YourKit 2024.9.

15. Large Array Facts (N1)

Measured array sizes from the dump, with a neutral 2 MB marker. The dump does not record the collector or region size, so this view makes no G1 humongous claims. Data: top-array samples and ArraysBySize.

16. Map Bucket Occupancy (L2)

Distribution of the current bucket proxy for HashMap/ConcurrentHashMap (non-empty buckets / table length). It hints at poor hashing or oversized tables; real collision chains need a per-map query. Data: map_collision_ratio (always-on).

17. DirectByteBuffer Owners & Capacity (B4 + P4)

Heap-dump-only view of NIO direct-buffer pressure using LeakIndicators.direct_byte_buffer_capacity_sum, direct_byte_buffer_cap_buckets, and top owner paths. This is capacity evidence, not process RSS.

18. Stale ThreadLocal Values (E2)

Demonstrates stale ThreadLocal evidence from dump data: null-key entries, value classes, and per-thread concentration. Uses thread_local_null_key_count plus captured value-class breakdown.

19. Finalizer Referents by Class (N2 + P2, P3)

Illustrates proposed finalizer referents grouped by class only when a supported java.lang.ref.Finalizer layout resolves each referent (P2). A separately verified Cleaner breakdown (P3) sits underneath. Registration is not a pending queue. Single dump; growth across dumps belongs in G1.

20. Pool State (P1)

Proposed decoding from verified pool fields in the dump: configured size, worker count and queued work. Busy/idle, throughput and latency are not established by a generic snapshot. Unknown library layouts show "not decoded", never zero. Primitive counters on a redacted dump cannot be trusted.

Must-have views without an earlier demo

21. Triage Digest with Coverage (H2 + H3)

The report's first screen: at most three findings, each with evidence and a link, followed by what was and was not checked. Views without data are listed as hidden, so "nothing found" never silently means "not checked".

22. Group Instances by Field Value (K5)

A guided query: pick a class and a field, see shallow bytes per value. Answers multi-tenant questions such as "which tenant holds most sessions?". The denominator is the selected class only.
